Matchii — a Go platform for an AI-native services marketplace

Full-Stack / AI Platform Engineer · Jul – Aug 2026

Matchii is an AI-native services marketplace. I designed the platform as a Go modular monolith with a Next.js front end, and kept one rule throughout: deterministic domain kernels stay separate from orchestration and I/O, so the parts that move money and state can be tested without the infrastructure around them.

Most of the work was about not doing things twice. The PostgreSQL schema grew to 115 tables over 89 migrations, with 185 foreign keys and 68 partial indexes; financial and workflow transitions go through append-only ledgers, idempotency keys, row locks and SQL compare-and-swap, so a retried request cannot push a payment or a booking forward a second time. Indexed pagination over 100k rows held 922 req/s at 64 ms p95. On a hot read endpoint I added a 60-second Redis cache and measured it with a reproducible A/B test (3 × 10k requests, 50 clients): throughput went from 6.1k to 8.6k req/s (+42%) and p95 latency from 11.1 to 7.2 ms (−35%).

Agents on the platform run on a six-state runtime and a DAG engine that is safe across multiple instances and restarts: tools are validated, approvals are durable, and runs are claimed with leases and heartbeats. A sweep every 30 seconds recovers up to 200 open runs per tick, and a 24-capability connector boundary keeps credentials out of agent code and gates every write.

To catch regressions before deployment I set up CI with 1,599 Go tests, 25 front-end contract checks, real Postgres and Redis, race detection, vulnerability scanning, and 8,192 permission combinations. Failure modes are explicit too: losing Postgres drains traffic, losing Redis degrades visibly while core jobs keep running.

M-PAC — a WhatsApp RAG assistant for a clinical programme

AI Engineer · Healthcare AI · Jan 2026 – present · Cantonese & Traditional Chinese

M-PAC is a 12-week exercise programme for 500 cancer survivors, delivered over WhatsApp in Cantonese and Traditional Chinese. The assistant answers participants' questions, and in a clinical setting a confident wrong answer is worse than no answer. So the RAG pipeline uses hybrid retrieval, requires an [S1]-style citation for every claim, routes by dialogue state, and runs a faithfulness check before any message is sent. Sensitive topics never get an AI answer; they are escalated to physicians.

The backend is split into six modules — scheduling, dialogue state, answer validation, retrieval, LLM access, and safety guardrails — in Node.js/TypeScript with Chroma and GPT-4o. It handles about 720 outbound and 360 inbound messages a day and 3,000–5,000 LLM calls a week, with a React admin console for monitoring conversations and managing enrolment, deployed on DigitalOcean/AWS.

Being-H0.5 — reproducing a frontier VLA model, and testing what pre-training buys

MSc Research Engineer at HKU, supervised by Prof. Taku Komura · Sep 2025 – Jun 2026

The first stage was reproduction. I brought the released codebase up from a fresh clone on a rented GPU server: the ZeroMQ inference server, the LIBERO benchmark under MuJoCo with headless EGL rendering, and later RoboCasa v0.2 with its pinned mujoco and numpy versions and mirrored assets. The released code had a few breakages along the way (an endpoint registered with the wrong signature, a missing modality_config method, float64 states crashing the server-side transforms), which I fixed and wrote up as an upstream patch. With the chain working, I evaluated the official 2B LIBERO checkpoint over 2,000 episodes: 98.6% on spatial, 97.0% on object, 98.0% on goal, and 95.0% on libero-10, in line with the paper.

The second stage was recreating post-training from base weights, without touching the released checkpoint. That meant a full fine-tune of InternVL3.5-4B (Qwen3-4B language backbone) with a Qwen3-4B action expert in the mixture-of-transformers layout and a flow-matching action head, on 4 GPUs with FSDP and gradient checkpointing. I wrote the launch scripts and runbooks myself, including auto-resume and checkpoint-saving policies, because rented instances can be stopped at any moment and an unsaved run is a lost run. I learned that one the hard way, once.

Midway through, the server moved to 4× RTX PRO 6000 Blackwell cards (compute capability sm_120), which the stock environment could not use at all. I migrated the stack to PyTorch 2.8 with CUDA 12.8 and changed five places in the model and training code to make it run on the new architecture: flash-attn became optional, attention switched to SDPA, the packed Qwen3 model got a gradient-checkpointing implementation it never had, flex-attention kernels got smaller block sizes to fit Blackwell's smaller shared memory, and a missing set_device call that put every rank on GPU 0 was fixed. After that, 4-card FSDP training ran stably at about 0.3 steps/s with roughly 92 GB in use per card.

The experiment I care most about came last. I wanted to test whether a larger backbone can make up for skipping the original human-centric pre-training, so I trained the 4B model from base weights and compared it with the official pre-trained 2B checkpoint. At 6k steps the from-base 4B reached 37.8% on LIBERO spatial; the pre-trained 2B sits at 95–98.6%. Doubling the parameters did not close the gap. My reading is that post-training alone cannot substitute for the pre-training stage, and I proposed follow-ups to separate the two effects cleanly: moving the comparison to RoboCasa, where scores are far from saturated, and measuring data-efficiency curves instead of a single end point.

On the side I also built a small proof of concept with Gemma-4-E2B as a frozen backbone plus a trained state encoder and action head. It settled two questions quickly: a prompt-only VLM is not a robot policy, and a small bolted-on action head is not enough either.

Skillios (ItsMyGoal) — an iOS goal planner with an agent inside

HKU COMP7506 group project · Group Leader · 2025 – 2026 · TestFlight beta

ItsMyGoal is a gamified goal planner. You give it a goal, an agent decomposes it into a skill tree of quests with prerequisites and XP, and the app tracks your todos, routines, and character progress on top. There is also a chat agent that plans real-world activities: it checks the weather, searches places, gets directions, and produces an itinerary that you confirm before anything is saved.

I was group leader for a four-person COMP7506 team (Cao Yuan, Wu Ziyang, Zhang Zihao). I split the work by skill stack: SwiftUI/SwiftData screens and gamification UI went to mobile-focused teammates; FastAPI routes, SQL sync schema, and deployment went to backend/database owners; demo video and XCTest documentation went to the testing track. I kept AI agent architecture, shared JSON contracts, and final integration.

The iOS client is SwiftUI with SwiftData as the source of truth. The agent loop runs on the device with about ten tools, parallel read-only execution, and serial database mutations. AI-created tasks always go through a confirmation sheet before they touch the database. The backend is FastAPI on PostgreSQL, deployed on AWS through CDK (ECS Fargate, RDS), with server-side Maps/weather proxies and an LLM proxy with per-user quotas.

KithAgent — a self-hosted agent gateway with filesystem-native memory

Personal project · Jun 2025 – present · built on OpenClaw + Hermes Agent + Pi Agent, orchestrated with Herdr

Kith comes from a daily annoyance: coding agents forget who you are between sessions, while the context that actually describes you lives in files on your machine. KithAgent is a self-hosted gateway that gives agents a memory made of those files.

Ingestion follows Andrej Karpathy's LLM Wiki pattern: raw sources stay immutable, an LLM maintains an interlinked Markdown wiki on top of them, and a schema governs what gets ingested and how. Each source is compiled into reusable knowledge once, instead of being re-chunked for every query. Non-text files are triaged by an LLM first, with over 90% routed correctly.

The human-readable files are the source of truth; the FTS5, vector and graph indexes are rebuildable from them. Retrieval fuses lexical, embedding and graph signals, reranks with a cross-encoder and does a second retrieval pass. That lifted recall from about 40% to about 78% (+38 pp), with precision, recall and F1 tracked across 19 pytest suites.

For long coding tasks I evaluated Herdr + Pi Agent for persistent parallel sessions and subagent decomposition, then added structured compaction and branch summaries so goals, decisions and file operations survive from one session to the next. It runs with Docker and local models through vLLM / LiteLLM.

Vibe-Trading — finance research agent with swarm teams

Open-source contributor · Jan 2026 – present · vibetrading.wiki · HKUDS/Vibe-Trading

Vibe-Trading is an open-source finance research agent from HKUDS. You ask a market question in plain language; the system routes skills and data sources, pulls live market data or broker journals, runs backtests and factor analysis, and returns a reproducible run card with evidence, metrics, tool traces, and caveats. It is built for research and simulation, not brokerage execution.

Its preset swarm teams — investment committee, quant desk, risk review, macro, crypto — run parallel specialist workers that debate and synthesize a single report. That is the same multi-agent mindset I explored in NL2BP, applied to finance. I used the system hands-on, then contributed reliability fixes upstream: 5 merged pull requests (#226, #227, #238, #239, #240) covering strict run-card JSON, retries for search connectors, yfinance end-date handling, and configurable timeouts.

Atari Portal — nine arcade games joined by a portal

Personal project · 2025 · play in browser

A retro arcade collection where nine classic-style games (Pac-Man, Breakout, Space Invaders, Frogger, Asteroids, Tetris, and three originals) connect through a portal system. Each game has its own trigger condition; meet it and a portal opens that warps you into the next game. On top of that sit story, arcade, and free-play modes, a coin economy with a small shop, a speed-boost mechanic for scoring streaks, and a global difficulty curve that climbs with every traversal.

Gameplay runs on Phaser 3, and the portal and glitch effects run on a Three.js overlay above it. Every texture is drawn with the Canvas API at boot and every sound is synthesized with the Web Audio API at runtime, so the build ships with no image or audio files at all. It deploys to GitHub Pages through GitHub Actions and also packages as an Electron desktop app for Windows and macOS.
